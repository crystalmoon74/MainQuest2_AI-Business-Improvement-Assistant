# 문제 정의서 — AI 업무 개선 요청 분석 Assistant

## 1. 도메인 설명
기업 내 **업무 혁신 / IT 기획(BA)** 영역. 현업 부서(구매·영업·총무·고객지원 등)가 "이 업무 좀 개선/자동화해 주세요"라는
요청을 올리면, IT 담당자 또는 업무 혁신 담당자가 요구사항을 파악하고 개선 방향(프로세스 개선, 시스템 개발, 교육 등)을
검토하는 **요구사항 접수·초기 분석 단계**를 다룬다.

## 2. 현재의 문제
| 지금 하는 방식 | 번거롭거나 비효율적인 부분 |
|---|---|
| 현업이 메일·메신저·양식에 자유롭게 요청을 적어 보냄 | 문제 설명이 모호하고 처리 빈도·시간·담당자·시스템 등 핵심 정보가 빠짐 |
| IT 담당자/BA가 요청을 읽고 질문 메일·미팅을 반복 | 요구사항 파악에 왕복 커뮤니케이션이 여러 번 필요 |
| 담당자마다 각자 방식으로 분석 메모 작성 | 문서 형식과 분석 수준이 요청마다 다름, As-Is/To-Be 기록이 남지 않음 |
| 요청 문장의 '느낌'으로 원인·절차를 짐작 | 확인된 사실과 추측이 섞여 잘못된 방향으로 개선이 시작될 위험 |

## 3. 개선 가설
> **요청 접수 직후** 단계에 LLM 기반 단일 분석 Agent(Google ADK + Gemini)를 넣으면,
> ① 비정형 요청을 표준 항목(업무 목적·AS-IS·문제점·개선 목적·개선 후보·To-Be)으로 즉시 구조화하고
> ② 빠진 정보를 체크리스트(빈도·처리시간·담당자·시스템·승인·예외·기대효과) 기준으로 찾아 **첫 질문 목록을 한 번에** 만들며
> ③ 모든 항목에 **확인/추정/미확인** 상태와 원문 근거를 달아 "사실 확정 오류"를 줄일 수 있다.
> 그 결과 BA의 초기 분석 시간이 줄고, 질문 왕복 횟수가 줄며, 보고서 형식이 표준화된다.

AI가 들어가는 위치:
```
현업 요청 입력 ─▶ [AI] 구조화 분석 ─▶ [AI] 누락 정보·질문 생성 ─▶ [코드] 근거 검증(가드레일) ─▶ 보고서 초안
                                                                            │
                         현업이 질문에 답변 ◀───────────────────────────────┘ ─▶ [AI] 재분석·보고서 갱신
```
AI는 **결정하지 않는다**. 개선 후보는 검토 후보로만 제시하고 최종 판단은 사람이 한다.

## 4. 대상 사용자
| 사용자 | 얻는 도움 |
|---|---|
| **IT 담당자 / BA (주 사용자)** | 요청을 읽자마자 구조화된 초안과 질문 목록을 받아 초기 분석 시간 단축 |
| 현업 담당자 | 무엇을 더 설명해야 하는지 질문으로 안내받아 요청 품질 향상 |
| 프로젝트 관리자 | 동일한 형식의 보고서로 여러 요청을 비교·검토 |

## 5. 성공 기준 (MVP)
| # | 기준 | 측정 방법 | 목표 |
|---|---|---|---|
| S1 | 입력→보고서 출력 정상 동작 | T01~T05 실행 | 5/5 성공 |
| S2 | 분석 시간 | `eval/run_eval.py`의 elapsed_sec | 건당 60초 이내 (PRD 7.3) |
| S3 | 초기 분석 시간 단축 | 같은 사례를 사람이 직접 분석한 시간과 비교 | 수작업 대비 50% 이상 단축 |
| S4 | 누락 정보 체크리스트 커버리지 | 7개 점검 범주 중 '확인' 또는 '질문'으로 다뤄진 수 | 사례당 7/7 |
| S5 | 질문 규칙 준수 | 질문 수 ≤ 10, 이미 확인된 범주 중복 질문 0 | 100% |
| S6 | 사실 확정 오류 | 가드레일이 잡은 '근거 없는 확인' 건수 + 사람 검토로 찾은 오류 건수를 기록 | 기록·공개 (0에 가까울수록 좋음) |
| S7 | 정보 부족 요청 대응 | T04에서 생성된 질문 수와 적절성 | 질문 6개 이상, 모두 업무 분석에 필요한 질문 |
| S8 | 현업/IT 경험자 피드백 | 5점 척도 "후속 분석에 바로 쓸 수 있는가" | 평균 3.5 이상 |
